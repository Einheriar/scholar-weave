# 再次开始审阅时重置旧结果与聊天

> 创建：2026-10-13
> 状态：修复与验证完成，用户已于 2026-10-13 授权提交与推送。

## 问题与依据

用户期望：已有审阅结果时，再次点击“开始审阅”应丢弃旧审阅结果与聊天记录，针对当前正文重新生成一份审阅。

已通过代码检查确认当前行为不符合这一预期：

- `src/app/page.tsx` 的 `runReview`（约第 653 行）在请求开始时只切换为 loading 并清除选中的建议，没有清除旧建议或聊天。
- 只有请求成功后才用返回的 items 替换 reviews；失败或取消时旧建议仍在。
- nodes、activeNodeId 和 chatTurns 在该流程中没有重置，旧聊天及其修改集仍可继续显示。
- `persistProjectNow` 保存整个 doc/reviews/nodes 现场，因此旧聊天还会随新建议继续落库，刷新或重新打开项目也会恢复。
- 现有测试覆盖单次审阅与聊天，缺少“已有建议和聊天后再次开始审阅”的回归场景。

## 已确认行为

1. 点击“开始审阅”且通过现有请求锁检查后，立即开始新一轮：清除当前项目全部旧建议、全部聊天节点和消息，包括全文、段落、选区与建议关联的对话。
2. 清除旧总结、选中建议、聊天活动节点、当前选区上下文、聊天报错及旧重试入口；关闭并使旧修改集预览失效，清除相关正文高亮。
3. 保留当前正文、标题、稳定 block ID 和项目 ID。已经接受并写入正文的修改保留，新审阅以当前正文为输入。其他历史项目不受影响。
4. 新请求成功后只显示新建议与新总结，聊天从空历史重新开始。
5. **新审阅失败或被取消时，也不恢复旧建议与聊天。** 清除动作是本轮开始时的明确结果；失败显示错误，取消回到空审阅状态，用户可再次发起审阅。
6. 按钮、Ctrl+Enter 与审阅失败后的重试入口统一走相同流程；保留既有请求锁、取消机制和响应版本校验。

本计划按用户提出的重新审阅语义直接执行清除，不额外新增确认弹窗。此处的等待批准来自用户本次要求：先写计划，同意后再修改。

## 实现范围

- `src/app/page.tsx`：在请求发出前集中重置审阅及聊天现场。同步更新 latestRef 和活动节点 ref，再更新对应 React 状态，防止异步保存读取旧结果。
- 处理修改集关闭的聊天展开状态恢复与退出动画，避免旧预览残留或关闭回调恢复旧现场。保持聊天高度及全文背景等用户偏好。
- 检查 `ContextChat` 的草稿作用域、时间线和附件生命周期，确保旧节点移除后界面与异步附件回调不继续挂在旧对话上。仅在必要时调整 `src/components/chat/ContextChat.tsx`。
- 清除后的现场需要保存，不能只在新审阅成功时标记待保存。复用现有保存机制，并检查在途旧保存与清除保存的顺序，防止旧快照回写。
- 成功后照常保存新建议。失败或取消后刷新、切换再返回，也应保持已清除的旧建议与聊天。
- 不改变 LLM 提示词、API 协议、Zod schema 或数据库结构。浏览器版与 Tauri 版通过共用页面逻辑获得同一行为。

## 验证与验收

优先扩展现有测试，使用 mock 响应，不调用真实模型：

1. 构造已有建议与多种聊天节点的项目，延迟新审阅响应。点击后立即断言旧建议、消息、节点与旧总结消失，正文和标题保持一致。
2. 请求成功后仅出现新建议，聊天保持空历史；旧错误重试和修改集入口不可继续执行。
3. 分别模拟请求失败与取消，断言旧记录不恢复，错误或取消状态正确，可以重新审阅。
4. 验证清除与成功后的持久化快照，以及已有保存未完成时不会留下旧记录。刷新或切换项目再返回后不复活旧记录，其他项目保持原内容。
5. 保留首次审阅、请求期间锁定、聊天新建节点等现有行为。

## 实施结果

- 旧修改集按既有退出动画关闭，清除高亮，关闭期间禁止接受旧修改；动画结束后释放预览对象并恢复聊天展开状态。
