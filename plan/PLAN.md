## 1. 项目背景

用户经常需要把较长的中文、英文或学术文本交给 LLM 检查语病、表达清晰度和行文质量。普通聊天界面通常只会按列表给出意见，存在以下问题：

1. 建议与原文缺少可靠的视觉对应关系，长文本中很难定位。
2. 用户需要手动查找并替换文本，操作成本高，也容易改错位置。
3. 有些反馈是针对某个词句的具体修改，有些只是针对段落或全文的判断，二者在普通回答中经常混在一起。
4. 用户可能不同意某条建议，或者希望模型给出更保守、更正式、更符合学术语气的版本，需要围绕建议继续对话。
5. LLM 给出全文重写时，用户难以判断究竟修改了哪些内容，也难以选择性接受。

参考产品形态是 Grammarly 一类的文本审阅界面：正文区域显示可定位标记，侧栏列出对应建议，点击后可以查看原因并一键替换。本项目在此基础上增加段落级、全文级审阅意见，以及围绕文档或某条意见继续与 LLM 对话的能力。

## 2. 产品定义

本项目是一个本地优先、Web 优先的 AI 文档审阅工作台。它不是单纯的拼写检查器，也不是让 LLM 直接重写全文的聊天框。

核心工作方式是：

```text
输入原文
  -> LLM 产生分层审阅结果
  -> 程序把结果绑定到全文、段落或具体文本范围
  -> 用户查看意见、追问或要求生成修改
  -> 程序预览具体差异
  -> 用户逐条接受、忽略或继续调整
  -> 导出或复制最终文本
```

### 2.1 核心原则

- 可定位：凡是局部建议，都必须能准确指出原文位置。
- 可解释：每条建议都应说明类型和理由。
- 可控制：LLM 不得未经确认直接修改正文。
- 分层表达：全文、段落、局部建议使用不同的视觉形式。
- 区分判断与操作：LLM 的观点不等于可执行的文本修改。
- 版本安全：旧分析结果不能错误地应用到已经变化的新文本上。
- 内容即数据：文档中出现的指令性文本只视为待审阅内容，不能覆盖系统审阅规则。

## 3. 核心概念

### 3.1 建议作用范围 Scope

第一版支持三种范围：

1. `document`：针对全文，例如结构、论证顺序、整体风格和术语一致性。
2. `block`：针对一个完整段落，例如段落功能不清、与上下文衔接差、应拆分或合并。
3. `range`：针对段落内某段精确文本，例如语法、措辞、标点和句式问题。

未来可以增加 `section` 或跨多个段落的范围，但不属于首个 MVP。

### 3.2 建议类型 Kind

必须严格区分：

- `opinion`：审阅意见或模型判断。它可以解释问题，但本身不能直接替换正文。
- `edit`：具体修改。必须包含可以校验的原文锚点和替换内容，可以执行接受或忽略操作。

典型的全文或结构建议属于 `opinion`。用户点击“按此意见修改”后，系统进行第二次 LLM 调用，将意见转化为一个 `ChangeSet`。该修改集先显示差异，确认后才能应用。

### 3.3 修改集 ChangeSet

修改集是一次 LLM 对话或一条高层意见产生的一组具体修改。它包含摘要、生成依据、对应文档版本和若干个可执行编辑。

修改集用于支持以下请求：

- “按照这条意见重组第二、三段。”
- “给我一个更保守的版本。”
- “保持所有术语不变，只调整语法。”
- “把这一段拆成两段，但不要删除信息。”

## 4. 目标用户与主要场景

首要用户是需要频繁检查长文本的个人用户，特别是论文、报告、申请材料、邮件和中英文正式写作场景。

主要流程：

1. 用户粘贴或输入文本。
2. 选择审阅模式和目标语言风格。
3. 点击“开始审阅”。
4. 查看全文总结、段落意见和局部修改。
5. 点击侧栏卡片，正文定位到对应位置；点击正文标记，侧栏定位到对应卡片。
6. 接受或忽略具体修改。
7. 对某条意见追问，或让 LLM 按该意见生成具体改动。
8. 预览修改集，逐条接受或全部接受。
9. 复制或导出修改后的文本。

## 5. MVP 范围

### 5.1 必须完成

- 纯文本和自然段编辑。
- 中文、英文文本均可处理。
- 三种审阅模式：仅纠错、适度润色、深度审阅。
- 全文、段落、局部三层建议。
- 审阅意见与具体修改的明确区分。
- 正文与侧栏建议双向定位。
- 局部文本高亮、段落标记和全文意见区域。
- 单条接受、忽略和撤销。
- 对某条建议、某个段落或全文发起上下文对话。
- 对话回复可以只解释，也可以产生待确认修改集。
- 所有修改先预览后应用。
- 文档版本校验和过期建议处理。
- 本地保存当前草稿、设置和最近一次审阅结果。
- 复制最终全文。

### 5.2 暂不实现

- 登录、付费和多用户系统。
- 多人实时协作。
- Word、PDF 和复杂富文本格式的无损导入导出。
- 浏览器扩展、Office Add-in。
- 原生移动应用。
- 离线本地模型管理。
- 自动后台改写全文。
- 完整版本控制或类似 Git 的文档历史。

## 6. 信息架构与界面

### 6.1 主界面

```text
┌──────────────────────────────────────────────────────────────┐
│ 文档标题 | 审阅模式 | 语言/风格 | 开始审阅 | 复制全文        │
├────────────────────────────────┬─────────────────────────────┤
│                                │ 全文审阅                    │
│ 文档编辑器                     │ 段落意见                    │
│                                │ 具体修改                    │
│ 局部建议显示下划线             │                             │
│ 段落建议显示左侧竖线或徽标     │ 卡片：解释、替换、忽略      │
│                                │                             │
├────────────────────────────────┴─────────────────────────────┤
│ 当前上下文：全文 / 第 3 段 / 建议 #8                        │
│ 针对当前内容询问 LLM……                             [发送]   │
└──────────────────────────────────────────────────────────────┘
```

### 6.2 建议显示规则

- 全文建议：显示在侧栏“全文审阅”区域，不给整篇正文画下划线。
- 段落建议：段落左侧显示竖线、圆点或编号；点击后高亮整个段落。
- 局部建议：使用不同颜色或线型的下划线；点击后选中对应范围。
- `opinion` 卡片使用“审阅意见”标签，主要操作是“继续询问”和“按此意见修改”。
- `edit` 卡片使用“具体修改”标签，显示原文、替换内容、理由，以及“接受”和“忽略”。
- 颜色不能作为唯一信息载体，还要使用图标、文字标签和可访问性属性。

### 6.3 侧栏筛选

建议支持以下筛选：

- 范围：全文、段落、局部。
- 类型：审阅意见、具体修改。
- 类别：语法、清晰度、风格、结构、逻辑、一致性。
- 状态：待处理、已接受、已忽略、已过期。

## 7. 对话设计

底部对话框根据当前选择自动确定上下文：

- 未选中任何内容：针对全文。
- 选中一个段落：发送该段、必要的相邻段落及全文摘要。
- 选中一条建议：发送建议内容、对应原文、所在段落、模型理由及必要上下文。
- 选中一段文字：针对该文本范围。

LLM 回复有三种合法形态：

1. `answer`：解释、比较或回答问题，不包含可执行修改。
2. `answer_with_review`：讨论已经收敛为一个具体方案时，包含解释和一条可由用户转入审阅列表的候选意见。
3. `answer_with_changes`：包含解释和一个待预览的修改集。

任何对话回复都不能直接改变正文。候选意见必须由用户点击“转为审阅意见”后才进入审阅流程；
修改集必须点击“预览修改”，再逐条接受或接受全部。

对话应支持的典型请求：

- 解释为什么提出某条建议。
- 生成更保守、更正式、更简洁或更学术的版本。
- 明确保留特定术语、引文、数字和专有名词。
- 将高层结构意见转化为多处具体改动。
- 撤回刚才的方向并要求新的方案。

## 8. 技术选型

### 8.1 首选方案

- 框架：Next.js App Router。
- 语言：TypeScript。
- UI：React。
- 编辑器：Tiptap，基于其 Decoration 和编辑事务实现标记与替换。
- 状态管理：优先使用 React 状态；复杂度上升后再引入 Zustand。
- 数据校验：Zod。
- 本地持久化：IndexedDB，建议使用 Dexie 封装。
- 样式：Tailwind CSS 或 CSS Modules，二选一并保持统一。
- LLM 接口：服务端 Route Handler，第一版接一个供应商，同时定义轻量 provider adapter。
- 测试：Vitest、React Testing Library、Playwright。

### 8.2 为什么先做网页

- 当前核心流程是“粘贴、审阅、修改、复制”，网页已经足够。
- Web 技术最适合实现复杂编辑器、侧栏卡片、差异预览和流式对话。
- 首版不需要系统级权限，做桌面程序不会增加核心价值。
- 如果未来需要托盘、全局快捷键、剪贴板读取或独立窗口，可以将前端适配为静态 SPA，再使用 Tauri 封装。LLM 服务调用需要迁移到 Tauri 后端、sidecar 或独立 API，不应假设 Next.js 服务端路由可以原样放入桌面壳。

### 8.3 API Key 与部署

- API Key 只能保存在服务端环境变量中，不能打包进前端代码或保存到浏览器 Local Storage。
- 本地个人使用时可以在本机运行 Next.js 服务。
- 若部署到公网，必须增加身份验证、请求限流和用量控制。
- 用户文档会发送给所选 LLM 供应商，因此界面需要明确的数据发送说明。

## 9. 建议的数据模型

以下结构是方向性设计，实施时可用 Zod Schema 作为唯一运行时协议来源。

```ts
type DocumentBlock = {
  id: string
  type: "paragraph"
  text: string
}

type DocumentState = {
  id: string
  title: string
  blocks: DocumentBlock[]
  revision: number
  checksum: string
  updatedAt: string
}

type ReviewScope =
  | { type: "document" }
  | { type: "block"; blockId: string }
  | {
      type: "range"
      blockId: string
      original: string
      prefix?: string
      suffix?: string
    }

type ReviewItem = {
  id: string
  documentRevision: number
  scope: ReviewScope
  kind: "opinion" | "edit"
  category:
    | "grammar"
    | "clarity"
    | "style"
    | "structure"
    | "logic"
    | "consistency"
  severity: "info" | "suggestion" | "important"
  title: string
  explanation: string
  replacement?: string
  status: "open" | "accepted" | "rejected" | "stale"
}

type ConcreteEdit = {
  id: string
  blockId: string
  original: string
  replacement: string
  prefix?: string
  suffix?: string
  explanation: string
  status: "pending" | "accepted" | "rejected" | "stale"
}

type ChangeSet = {
  id: string
  sourceReviewId?: string
  documentRevision: number
  summary: string
  edits: ConcreteEdit[]
}

type ChatContext = {
  type: "document" | "block" | "range" | "review"
  blockId?: string
  reviewId?: string
  selectedText?: string
}
```

约束：

- `kind: "opinion"` 时不得包含可直接执行的 `replacement`。
- `kind: "edit"` 时必须包含 `replacement`，并且应使用 `range` 或完整 `block` 作为范围。
- 全文结构调整必须先生成 `ChangeSet`，不能用一个全文 replacement 绕过差异预览。

## 10. 文本定位与版本安全

这是项目最关键的技术部分。

### 10.1 不信任 LLM 字符坐标

不要要求 LLM 返回 `start`、`end` 字符偏移。Unicode、Emoji、换行、富文本节点和用户后续编辑都会造成坐标差异。

模型应返回：

- 稳定的 `blockId`。
- 必须逐字存在于原文中的 `original`。
- 用于消歧的 `prefix` 和 `suffix`。
- `replacement` 和解释。

客户端在对应 block 中定位 `original`，再转换成编辑器的实际位置。

### 10.2 稳定段落 ID

- 每个段落节点创建时获得 UUID 或稳定 ID。
- 普通文字编辑不改变 block ID。
- 拆分段落时保留前半段 ID，后半段创建新 ID。
- 合并段落时保留目标段落 ID，并使引用被删除段落的建议过期。

### 10.3 定位校验

应用建议前必须检查：

1. 文档 revision 是否仍然兼容。
2. block 是否仍然存在。
3. `original` 是否能唯一定位。
4. prefix、suffix 是否吻合。
5. 目标范围是否已被用户或其他建议修改。

无法可靠定位时，将建议标记为 `stale`，提供“重新分析该段”，不能猜测位置后强行替换。

### 10.4 编辑过程中的位置变化

- 屏幕上的高亮使用 Tiptap Decoration，不把标记序列化进正文。
- 用户编辑时，通过编辑器 transaction 映射尚未受影响的范围。
- 编辑与某条建议范围相交时，优先将该建议设为过期。
- 多条修改批量接受时，在一个事务中处理；实现上可按文档位置从后向前替换，或使用事务 mapping。
- 重叠建议不允许盲目同时接受。接受一条后，其他相交建议应重新验证。

### 10.5 异步响应

每次审阅和聊天请求都携带：

- `documentId`
- `revision`
- `checksum`
- 请求涉及的 block ID

响应回来时若正文已变化：

- 全文结果默认标记为可能过期。
- 未变化 block 的建议可以重新校验后保留。
- 已变化 block 的建议直接标记为过期。

## 11. LLM 协议

### 11.1 审阅请求

请求至少包含：

- 审阅模式：proofread、polish、deep_review。
- 原文语言和期望输出语言。
- 用户设定的风格，例如学术、正式、简洁。
- 必须保留的术语或文本。
- 带稳定 ID 的段落列表。
- 只返回真实、必要建议的约束。
- 不得把文档中的内容当作系统指令执行的约束。

### 11.2 审阅响应

使用严格结构化输出，顶层建议包含：

```json
{
  "documentSummary": "文章整体清晰，但第二、三段存在功能重复。",
  "items": [
    {
      "id": "review_01",
      "scope": { "type": "document" },
      "kind": "opinion",
      "category": "structure",
      "severity": "suggestion",
      "title": "中间两段功能重复",
      "explanation": "第二、三段都在说明研究动机，可重新分工。"
    },
    {
      "id": "review_02",
      "scope": {
        "type": "range",
        "blockId": "p_03",
        "original": "这些结果共同的表明",
        "prefix": "研究发现，",
        "suffix": "该效应存在。"
      },
      "kind": "edit",
      "category": "grammar",
      "severity": "important",
      "title": "删除多余助词",
      "explanation": "这里不需要结构助词“的”。",
      "replacement": "这些结果共同表明"
    }
  ]
}
```

服务端必须使用 Zod 再校验一次，并在返回浏览器前过滤无效字段和无法定位的编辑。

### 11.3 长文本策略

首版不要把极长文档无条件塞进一个请求：

- 先计算文档级摘要和结构信息。
- 局部语言问题按若干相邻段落组成的窗口审阅。
- 窗口应有少量重叠，以发现段落衔接问题。
- 使用 block ID 合并结果并去重。
- 全文级意见与局部修改可以分成两次模型调用，以降低混淆。

在文本不长时可以先采用单次调用，以尽快完成 MVP；但数据协议从一开始就应支持分批结果。

## 12. 服务端接口

建议的首版接口：

### `POST /api/review`

输入文档版本、段落和审阅设置；输出结构化 `ReviewItem[]`。

### `POST /api/chat`

输入当前聊天上下文、必要文档片段、关联建议和消息历史；输出纯解释、候选审阅意见或解释加修改集。

### `POST /api/change-set`

将某条 `opinion` 和用户补充要求转化为可执行 `ChangeSet`。如果 `/api/chat` 已能可靠覆盖这一功能，可以后续合并接口，但 MVP 阶段分开更容易测试。

所有端点都需要：

- 输入长度限制。
- Schema 校验。
- 结构化输出若仅有 JSON 语法或 Schema 结构错误，自动请求模型纠错一次；网络、超时、鉴权或供应商错误不自动重试。
- 自动纠错仍失败时返回可辨识的统一错误，前端保留原上下文并提供手动重试，聊天重试不得重复写入用户消息。
- 超时和取消处理。
- 统一错误结构。
- 不向客户端返回密钥或供应商内部错误详情。
- 对日志中的正文进行最小化或脱敏，默认不记录全文。

## 14. 实施阶段

### 阶段 0：项目初始化

目标：建立可运行、可测试的基础工程。

- 创建 Next.js + TypeScript 项目。
- 配置格式化、类型检查和基础测试。
- 安装 Tiptap、Zod 和本地存储依赖。
- 创建 `.env.example`，不提交真实密钥。
- 将本计划放到项目根目录。

验收：开发服务器可运行；类型检查和空测试套件可通过。

### 阶段 1：编辑器与稳定段落

目标：先解决文档模型，不接 LLM。

- 实现自然段编辑器。
- 为每个段落生成稳定 block ID。
- 实现文档 revision 和 checksum。
- 实现粘贴、编辑、拆分、合并和本地保存。
- 编写 block ID 行为测试。

验收：常见编辑操作不会无故改变未受影响段落的 ID；刷新后能恢复草稿。

### 阶段 2：静态建议原型

目标：用固定假数据验证 Grammarly 式交互。

- 实现全文、段落、局部建议的不同显示方式。
- 实现 Tiptap Decoration。
- 实现正文与侧栏双向定位。
- 实现筛选、接受、忽略和撤销。
- 实现过期建议的视觉状态。

验收：不依赖 LLM，也能完整演示建议定位和替换流程。

### 阶段 3：LLM 审阅

目标：接入真实结构化审阅结果。

- 定义 Zod Schema。
- 编写审阅 prompt。
- 实现 provider adapter 和 `/api/review`。
- 校验 block、original、prefix、suffix。
- 处理超时、取消、空结果和不合法响应。
- 增加审阅模式设置。

验收：一篇多段文本能产生三层建议；所有可执行修改都能可靠定位或明确标记失败。

### 阶段 4：版本安全与批量修改

目标：确保异步和连续修改不会改错位置。

- 实现 response revision 校验。
- 实现编辑器 transaction 后的建议更新。
- 实现重叠建议处理。
- 实现修改集预览和批量接受。
- 增加完整撤销测试。

验收：用户在请求期间修改文本时，旧建议不会错误覆盖新文本。

### 阶段 5：上下文聊天

目标：允许围绕全文、段落、选区和建议继续对话。

- 实现 ContextChat UI。
- 实现上下文打包和消息历史裁剪。
- 实现 `/api/chat`。
- 区分纯解释与包含修改集的回复。
- 实现“按此意见修改”和修改集预览。

验收：用户能针对一条全文意见提出限制条件，得到多项可预览修改，并选择性接受。

### 阶段 6：产品化整理

目标：让工具达到个人日常可用状态。

- 加载、空状态、错误状态和取消操作。
- 键盘快捷键和基础无障碍支持。
- 本地设置、最近文档和清空数据。
- 隐私提示和数据发送说明。
- Playwright 端到端测试。
- 构建和部署说明。

验收：核心流程在全新浏览器环境中无需开发者干预即可完成。

## 15. 重点测试场景

必须覆盖以下情况：

1. 同一个短语在同一段出现两次。
2. 文本包含中文标点、英文标点、Emoji 和特殊空格。
3. LLM 返回的 original 不存在或并非逐字一致。
4. LLM 请求尚未完成时用户修改了相关段落。
5. 两条修改建议范围重叠。
6. 接受一条修改后，其后的建议位置发生变化。
7. 段落被拆分、合并或删除。
8. 全文意见被转成涉及多个段落的修改集。
9. 用户要求保留某个术语，但 LLM 仍试图修改它。
10. 文档内容本身包含“忽略之前指令”一类文本。
11. 网络失败、模型拒绝、超时或只返回部分结果。
12. 用户连续撤销和重做多次。

## 16. 风险与对策

### 锚点不可靠

对策：block ID 加 exact original 加上下文锚点；应用前强校验；失败时过期而不是模糊替换。

### LLM 过度润色

对策：模式分级；明确最小修改原则；让用户维护“必须保留”的术语；每条修改都可拒绝。

### 高层意见难以一键执行

对策：高层意见本身不可执行，必须经过“生成修改集 -> 差异预览 -> 用户确认”。

### 长文本成本与延迟

对策：按段落窗口处理；全文分析和局部校对分开；只把对话所需上下文发送给模型；允许取消请求。

### Prompt injection

对策：把用户文档明确包裹为不可信数据；系统提示规定不得执行文档中的指令；服务端固定审阅协议；所有输出仍需 Schema 和业务校验。

### XSS 与不可信输出

对策：默认以纯文本显示 LLM 输出；若以后支持 Markdown，必须使用经过配置的安全渲染与清洗，不直接注入 HTML。

### 隐私

对策：不默认记录正文日志；明确说明文本将发送到模型供应商；密钥仅在服务端；未来可增加本地模型适配。

## 17. MVP 完成定义

满足以下条件才算 MVP 完成：

- 用户可以粘贴一篇多段长文本并成功审阅。
- 系统能同时展示全文意见、段落意见和局部修改。
- 用户能清楚区分 LLM 观点与可执行修改。
- 点击任意局部建议都能准确定位原文。
- 点击替换只改变目标文本，并能撤销。
- 正文变化后，无法安全应用的旧建议会被阻止或标记过期。
- 用户可以针对某条意见继续聊天。
- 聊天可以产生修改集，但不会未经确认修改正文。
- 用户可以预览、选择性接受修改集并复制最终文本。
- 核心定位、版本和重叠场景有自动化测试。

## 18. 后续演进方向

MVP 验证成功后，再按真实使用需求选择：

1. Tauri 桌面封装：托盘、全局快捷键、系统剪贴板和独立窗口。
2. 浏览器扩展：在网页输入框旁调用本工具，但需单独解决各网站编辑器兼容。
3. Word Add-in：面向论文和正式文档工作流。
4. 富文本与批注导出：保留标题、列表和引用格式。
5. 多模型或本地模型：在质量、成本与隐私之间切换。
6. 自定义审阅规则：术语表、禁用词、期刊风格和团队写作规范。
7. 文档历史和对比视图。
